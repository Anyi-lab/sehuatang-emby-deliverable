## 一、一句话结论

Emby 播不了 strm 的根因：strm 里的地址指向 115-Desktop 的 **`/d/`（下载路由，恒 302）**，
该直链签名**绑定请求方 User-Agent**；Emby 取链与取流两跳 UA 不一致 → **403**。
修法：全库 strm 的端口 **11500 → 11501**，落到本地中继 `strm-relay`（固定 UA 取链+取流），
已实测 Emby `stream?static=true` → **206 / video/mp4 / ftyp isom**。

不是 Emby 的锅，也不是「本地代理」设置没生效——那个设置**只作用于 `/play/`**，与 strm 走的 `/d/` 无关。

## 二、现在这条链路长什么样

```
播放器 / 手机 / 小欢影视
   └─► Emby（Windows，http://192.168.2.238:8096 或 172.25.224.1:8096）
          └─► 读 G:\srtm\...\xxx.strm
                 └─► http://192.168.2.238:11501/d/<pickcode>/<URL编码文件名>
                        └─► Windows portproxy 11501 ─► WSL  strm_relay（0.0.0.0:11501）
                               └─► 固定 UA 向 http://192.168.2.238:11500 要直链（拿 302）
                                      └─► 跟随到 115 CDN，把字节流回给 Emby / 客户端
```

三条关键事实：

1. **strm 永远走 `/d/`**（115-Desktop 的 `/d/` 恒 302，与 `转发策略` 设置无关）。
2. **`/play/` 才是流式路由**（内置播放器走它，所以"切成本地代理就秒好"）。
3. **中继不看客户端 UA**，所以「全库播放现在唯一依赖 = WSL 里的中继活着」。

## 七、待决 / 未做（按优先级）

> ⚠️ **重启后第一件事**：上面第五节的「新生成 strm 默认端口」改动，需要服务重启才生效。
> 关机再开机时 systemd 会自动拉起，**不用手工操作**——但如果你在重启前就用手工脚本
> （`backfill_scrape.py` 等）生成过 strm，那批要看一眼端口是不是 11501。
> 校验一条命令：`grep -rl ':11500/' /mnt/g/srtm --include='*.strm' | wc -l` → 期望 0。

1. **中继是单点**：WSL 或服务挂了 → 全库不播。可接受就先这样，不能接受要搞双活/看门狗。
2. **省带宽方案**：中继加 `--mode redirect`（UA 回显后对客户端发 302，字节零中转）。**未实现**，且挑客户端。
3. **`/play/` 方案**：strm 指向 `:11500/play/`，吃 115-Desktop「本地代理」设置，零中转；代价是设置一旦切回
   「302重定向」或应用更新重置 → 全库立刻不播。与当前方案只差改一个字段，随时可切。
4. **光鸭盘** 51 个 strm 指向 `127.0.0.1:8233`（对应服务未运行）。
5. **端口冲突**：115-Desktop 的 WebDAV 默认端口 = 11501 = 中继端口（WebDAV 当前关闭，别开）。
6. **Clash Party（mihomo）回环直连规则未改**：仅剩告警，不影响播放。
7. **是否切回 Jellyfin**：用户反馈以前 Jellyfin 播 strm 无此问题（推测因客户端直连、取链取流同一身份）。
   建议：先在**一个小子集**上并行跑 Jellyfin 做 A/B，再决定迁移（迁移成本：8596 条重扫 + 6 个库重建 + 客户端全部改连）。
8. **115 风控**：不要对整库做 Emby 全量刷新 / ffprobe 全扫（8596 次取链会放大 115 API 调用，`770004` 风险）。
