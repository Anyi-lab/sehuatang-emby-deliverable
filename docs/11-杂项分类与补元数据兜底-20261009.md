# 11 · 「杂项」分类 + 补元数据兜底建目录 — 2026-10-09

## 起因

用户在帖子页点 📤 上传元数据，收到：

```
❌ 上传失败: 未定位到 Emby 电影库目录 (已刮削/<分类>): thread=3820431
   title=俄罗斯顶级Coser甜狐姐「Sweetie Fox」，She
```

两个缺口叠加：

1. **MDC 刮不到** —— `www.98T.la@Sheer.24.07.20.…strm` 被解析成番号 `SHEER.24.07.20`，
   去 ThePornDB / Javdb 并行抓取，两边都「未找到详情页」→ `元数据获取失败`，
   因此 **没有在 `已刮削\欧美` 下建任何目录**，strm 留在 `待看\sehuatang_ea\thread_3820431`。
2. **补元数据不能建目录** —— `_find_emby_movie_dir()` 只认「MDC 已产出的目录」：
   ① inode 硬链接比对（目标区无匹配）② 番号候选（欧美名抠不出 JAV 番号）。
   两条路都空 → 按注释「绝不退化成写旧路径」直接回 404。

即 **只有 MDC 成功刮过的条目才能补元数据**，恰好把最需要它的那类堵死了。
用 `PENDING_MD_SQL` 查库，「待补元数据」当时积压 **30 条**（跨国今天三条欧美、
09-29 一批 GVG-*、09-27 FC2/欧美若干），是通病不是孤例。

## 改动

用户需求：**给这类「没元数据、只能手动刮」的杂片单独一个分类**。

### 1. 新分类 `misc`（显示名「杂项」）

`import_api.py · CATEGORY_MAP`：

```python
MANUAL_CATEGORY = 'misc'
MANUAL_ROOT = '/mnt/g/srtm/已刮削/杂项'
...
'misc': ('/mnt/g/srtm/待看/sehuatang_misc',  MANUAL_ROOT,  '杂项'),
```

- 115 落点 `/sehuatang/杂项/thread_x` → 本地 `待看/sehuatang_misc/thread_x`
- **MDC 不 watch 这个目录**（`watch_dirs` 里没有它）→ 流水线只到 strm 落地
- 消费端：Emby 新建 **movies 库「杂项」**，路径 `G:\srtm\已刮削\杂项`
- 面板首页 / 任务页 / 油猴下拉的分类表都从 `CATEGORY_MAP` 注入 → 自动出现
  （油猴的 `CAT_OPTIONS` 是硬编码，已手工加 `<option value="misc">杂项(手动刮)</option>`，v1.15.2）

### 2. 杂项分类跳过 MDC 等待

`misc` 没有 MDC watcher，等 300s 必然超时。在 import 流程的 `skip_mdc` 判定里加一支，
直接进入「strm 就位、等帖子页补元数据」的终态。

### 3. 补元数据兜底建目录（核心修复）

新增 `_fallback_entry_name()` + `_fallback_emby_movie_dir()`，接在 `_handle_metadata()`
fanhao 分支原本直接 404 的位置：

```
_find_emby_movie_dir() 未命中
  → _fallback_emby_movie_dir()
      取待看区 .strm → 推导条目名 → 在 已刮削/杂项/<条目名>/ 建目录
      → os.link() 硬链接 strm（保留 inode；失败退化为 copy）
  → 继续原有流程：写 poster/fanart/backdrop → 写 movie nfo → 定向刷新 → 扫库
```

条目名推导顺序（对齐 MDC 自己的 `{{number}}` 模板）：
番号 → `片商.YY.MM.DD`（欧美式，文件名优先、帖子标题兜底）→ `YY.MM.DD` → 文件名主干。

**国产（`cn`）不进兜底** —— 用户在 2026-09-27 明确「国产再也不进 Emby 库」，
兜底对它保持原 404，避免绕开那个决定。

**硬链接而非拷贝**：MDC 整理用的就是硬链接，保留 inode 才能让
`_find_emby_movie_dir` 的 inode 匹配、以及 🎬 MDC 重跑继续有效。实测同一 inode、link count=2。

### 4. 杂项库排除在「跨分类兜底」之外

`_wait_mdc_scrape` 的 `alt_roots` 和 `_find_mdc_output_across` 的 `roots` 都要排除 `MANUAL_ROOT`：
`_find_mdc_output` 在「候选番号为空」时会用「目录 20 分钟内被创建」当命中判据，
而杂项里的目录恰好是 strm+nfo+图片齐全的手动产物 → 会被误当成「MDC 刮好了」，
让真正刮不到的条目假装成功、不再提示补元数据。

## 修复 2 · 「目录已存在」被误判失败（2026-10-09 18:30）

上线后实测发现：**同一个条目第一次点 📤 成功、第二次点必失败**。

```
[metadata] 兜底建目录失败: thread=3820431 (link-failed:/mnt/g/srtm/已刮削/杂项/Sheer.24.07.20)
```

原因在 `_fallback_emby_movie_dir()` 的搬运循环：目标是 `if os.path.exists(dst): continue`，
strm 上一轮已经硬链接过去了 → `linked` 和 `copied` 都还是 0 → 末尾
`if not linked and not copied: return None, 'link-failed'` 直接判失败 → 又回 404，
海报永远补不上。（这条目录是开发时测试先建好的，用户第一次点就撞上了。）

改为三态计数：

- 目标已存在且**同 inode 或同大小** → `present += 1`，视为已就位，不算失败；
- 目标已存在但内容不同 → 删掉重链；
- 只有在「没链上、没拷上、也没有一个已在位」时才报 `link-failed`。

顺带修了刷新的空转：兜底新建目录时 Emby 还没扫到，第一次 `_refresh_emby_path` 必然
`items=0`（旧日志里三条全是 `items=0`）。现在扫库广播之后再重试最多 3 次 × 2s，
命中即停 —— 海报/简介当场生效。

验证：

```
POST /api/metadata {thread_id:"3820431", title:...}
→ 200 {"dir":".../杂项/Sheer.24.07.20",
        "matched":"planned-by-fallback(fallback-created(hardlink=0,copy=0,existing=1); was …)",
        "refreshed":true,"items_refreshed":1}
```

## 修复 3 · 「补完了还显示待补元数据」（2026-10-09 18:40）

用户补完元数据，任务页那一行仍然写「待补元数据 80%」，看着像没补上。实际**补是补上了**
（poster + 简介 + nfo 都已落盘、Emby 已挂图），是**面板判据把自己判错了**。

`isPendingMeta()` / `PENDING_MD_SQL` 的规则是「`status='done'` 且 `step<>'scan'` = 等油猴补元数据」。
而 📤 元数据这条路写监控记录时用的就是：

```python
save_task(..., status='done', step='metadata', kind='metadata')
```

`step='metadata'` 永远不等于 `'scan'` → **这条「我刚刚补好元数据」的记录，自己被标成了「待补元数据」**。
于是用户每补一次，清单里就多一条待补，越补越多 —— 用户看到的四条全是 `kind=metadata` 的行。

同源的第二个毛病：📤 结束后会调 `_start_prewarm()`，它按
`ORDER BY created_at DESC LIMIT 1` 取该帖最新一条记录，而这正好是**上一次 📤 自己的行**，
于是把上一条「📤 元数据补充」的行改写成了「入库完成 / step=scan」——
面板上同一帖出现一行「已完成」一行「待补元数据」，更让人以为是没补上。

### 改动

1. `PENDING_MD_SQL` 加 `AND IFNULL(kind,'')<>'metadata'`；
2. 前端 `isPendingMeta()` 加 `&& t.kind!=='metadata'`（同一判据的前端副本，两处必须同步改）；
3. `statusCell()` 给这类行单独一个徽章：**「已补充」**（title: 元数据已写入媒体库，无需再补）；
4. `_start_prewarm()` 取行的 SQL 加 `AND IFNULL(kind,'')<>'metadata'` —— 预热/收敛只允许
   改写**入库行**（`fanhao`/`non_fanhao`/`mdc`），不许覆盖 📤 自己的记录。

### 验证

```

修复后 pending_md = 46   ← 被排除的 4 条全是 📤 元数据行 (3779674 / 3820460 / 3820436 / 3820431)

GET /api/import/list?pending_md=1 → 剩下的全是真·未补条目 (GVG-680-C / gvg-695 / …)
```
