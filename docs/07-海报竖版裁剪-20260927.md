## Emby 怎么「识别」图片类型：靠文件名，不看内容（实测）

**结论：Emby 不分析图片内容、不看比例、不猜横竖。每个条目下有一组固定槽位（ImageType），槽位靠
「目录里有哪些文件名」推出。** 槽位与文件名是硬映射，实测证据：

| Emby 槽位 | 认这个文件名 | 期望形状 | 客户端视图菜单里的名字 |
|---|---|---|---|
| Primary | `poster.jpg`（`cover.jpg`/`folder.jpg` 不会额外加，同类型只取一个） | 2:3 竖版 | 海报 |
| Thumb | `thumb.jpg` | 16:9 横版 | 缩略图 |
| Backdrop | `fanart.jpg` / `backdrop*.jpg`（可多张） | 16:9 | 详情页背景 |
| Banner | `banner.jpg` | 宽条 | 横幅图 |
| Disc | `disc.png` / `discart.png` | 1:1 圆盘 | 光盘封面 |
| Logo | `logo.png` / `clearlogo.png` | 透明 PNG | 徽标 |

实测过程（条目 `欧美/无码B 系列/Blacked.16.08.18`，ItemId 22767）：

```bash
# 直接看 Emby 认到的槽位 ← 文件名
curl -H "X-Emby-Token: $KEY" "http://172.25.224.1:8096/emby/Items/22767/Images"
# 往目录放入 banner.jpg / logo.png / disc.png / clearlogo.png / backdrop1.jpg
# POST /emby/Items/22767/Refresh  {"ImageRefreshMode":"FullRefresh","MetadataRefreshMode":"None"}  → 204
# 再查 /Images：Banner←banner.jpg、Logo←clearlogo.png、Disc←disc.png、Backdrop 两张
# 删掉这些文件再刷新：槽位随之消失，只剩 Primary/Thumb/Backdrop
```

推论（也是这轮「横图」问题的真正机理）：

1. **图放在哪个槽位由文件名决定，槽位的期望比例是固定的**。把 16:9 的欧美封面写进 `poster.jpg`，
   Emby 就按 2:3 的「海报」框去裁切/拉伸显示 → 看着是被压扁的横图。**不是 Emby 认错，是图放错了槽位。**
2. 我们库里只有 `poster.jpg` / `thumb.jpg` / `fanart.jpg` 三种文件，所以：
   - 「海报」「缩略图」视图有真图；
   - 「横幅图」「光盘封面」「徽标」三个视图**槽位不存在**（`/Images/Banner` 等返回 404），客户端回落到 Primary
     → 三个视图看起来一样，属正常现象，不是缺图。
3. 欧美条目的 `thumb.jpg` 是 1000×562 横图——**这是对的**（Thumb 槽位本来就是 16:9），不能拿它当海报。
4. mdc-ng 侧不存在「识别横图」这回事：它只有人脸/中心裁（`CropType` 枚举 `不裁剪/人脸识别/中间裁剪/右侧裁剪`），
   `crop_type_uncensored=Center` 是**无条件归一化到目标比例**，谁多出来的方向就居中裁谁；官方竖版海报在
   `crop_poster=false` 时原样保留、不被触碰。「先判定横幅、只裁横图」只能在我们这一层做
   （`scripts/scan_all_posters.py` 已能按比例判定，接个每日巡检即可）。

## 附：为什么会出现「缩略图和海报混在一起」（2026-09-27 取证）

现象：欧美 / 无码 库点进去，同一屏里一部分卡片是竖的（海报），一部分是横的（看着像缩略图）。

根因：**默认的「海报」视图并不是把每张图硬塞进 2:3 框，而是先按该项 Primary 图自己的宽高比决定卡片形状。**

前端源码（Emby Web 4.10，`/web/modules/`）：

```js
// tabbedview/listcontroller.js
prototype.getCardOptions = function (items, settings) {
  if ("banner" === settings.imageType) shape = "banner";
  else if ("disc" === settings.imageType) shape = "square";
  else if ("logo" === settings.imageType) shape = "backdrop";
  else if ("thumb" === settings.imageType) shape = "backdrop", preferThumb = !0;
  else shape = "auto";            // ← 海报视图走这里
  ...
};

// cardbuilder/cardbuilder.js
autoShape = ("auto" === shape),
items = shape = autoShape ? _imagehelper.getShape(items, options) : shape;   // ← 按实际比例定形状

// common/imagehelper.js
function getShapeFromAspect(ar) {
  return ar >= 3   ? "banner"
       : ar >= 1.4 ? "backdrop"      // 16:9 横卡 —— 视觉上就是「缩略图」那种
       : ar >  1.2 ? "fourThree"
       : ar > 0.73 ? "square"
       :             "portrait";     // 2:3 竖海报
}
getShape: (items, options) => getShapeFromAspect(getPrimaryImageAspectRatio(items, options)) || options.defaultShape || ...
```

即：**横图 → 宽卡（看着像缩略图）；竖图 → 海报卡。** 两形状混在一页，就是当初看到的混排。

实测证据：

| 对象 | 尺寸/比例 | Emby 认定的 shape |
|---|---|---|
| 备份里的原图（`/mnt/g/srtm/_归档/_backup_20260927_poster_crop23/`） | 1000×562 / 800×450 → 1.778 | backdrop（宽卡） |
| 裁剪后的 poster.jpg | 848×1200 → 0.706 | portrait |
| 现在两个库的 API 实测 | 欧美 29/29、无码 16/16 全部 `PrimaryImageAspectRatio ≈ 0.66~0.71` | 全部 portrait |

```bash
# 取证命令
python3 /tmp/emby_aspect.py       # 列两库每条 item 的 PrimaryImageAspectRatio + ImageTags + shape
```

两条推论：

1. **竖版裁剪同时解决了两个问题**——不再被裁掉，且卡片形状自然统一；不需要额外去「统一视图」。
2. `PrimaryImageAspectRatio` 是 **Emby 服务器算好并缓存在库里**的字段（API 里能直接读到）。换图后必须刷新条目/媒体库，否则卡片形状还是旧比例 → 会出现「文件已经改了但还是混」的假象。

## 方向回退：竖条 → 完整横图（2026-09-27 傍晚 · 最终状态）

### 用户反馈与根因

竖版化之后新问题出现：**卡片上只显示海报的中段**。最典型的 `欧美/无码T 系列/TeamSkeetLabs.24.01.24`：
源封面是一张带大字标题的设计图，被裁成 848×1200 的窄竖条后，标题「ARE YOU CUMMING?」只剩中间一截。

根因在本文 Part 2 里已经查清：Emby「海报」视图其实是 `shape = "auto"`，**按 Primary 图自己的宽高比决定卡片形状**。
竖条（AR≈0.71）被判成 `square`（0.73 以下才继续降到 portrait），卡片是方的，于是窄竖条只在方块里显示中段。
换句话说：**不是裁得不对，是「裁成竖版」这条路本身不适合欧美源的横版设计封面。**

### 决定

**欧美 / 无码 两库的 `poster.jpg` 直接用完整横图（缩略图风格），接受卡片变成宽卡。**
规则（与 `poster_to_wide.py` 一致）：

1. `poster.jpg` 是竖的（AR < 1.4）
2. 目录里有横图：`thumb.jpg` → `fanart.jpg` → `backdrop.jpg`，取第一个 AR > 1.4 的
3. **且该横图宽度 ≥ 原竖海报宽度**（防止越换越糊）
4. → 旧 poster 移到备份目录，横图 `copy2` 成新的 `poster.jpg`

| 项 | 数值 |
|---|---|
| 成功替换 | **40 / 42 条**（39 条批量 + 此前手工试改的 Blacked.20.01.10） |
| 无码库 | 13/13 横图 |
| 欧美库 | 27/29 横图 |

两条换不了的（都是**没有可用横图**，不是脚本失败）：

  （宽 640 < 1000，被「防降质」规则拦下）。

两条都想救的话只能**从视频本体抽帧重做横图**，未做。

**备份**：旧海报按相对路径保留在 `/mnt/g/srtm/_归档/_trash_海报换缩略图_20260927/<库>/<目录>/poster.jpg`（40 个）。

**Emby 侧**：逐条 `POST /Items/{id}/Refresh` 后核验（`PrimaryImageAspectRatio` 是服务器缓存字段，不刷新不生效）。
`AV / FC2 / 里番 / 自存 / 丝袜 / 国产自拍` 是原生竖版封面、显示完整，**未动**。

### 为什么又出现「混排」

这次的混排是**有意为之**：40 条宽卡 + 2 条竖卡，加上其它库的竖卡。用户要的是「海报别被切」，不是「形状统一」，
所以不再追求形状一致。

# 续二：海报体检页 `/posters`（2026-09-28 晚，面板第四个页面）

## 一、为什么加这一页

前面两轮把「竖条海报 → 横图」修了两层：**改 MDC 全局配置**（`crop_type_uncensored=None`）
+ **入库钩子**（`import_api._poster_wide_fix`）。但这两层都是「事后默默修」，
有问题时看不出来：

- 新入库又被裁回竖条 → 只能靠翻目录、跑 `poster_audit.py` 命令行才知道；
- 修完之后 Emby 侧有没有生效（卡片形状变没变）→ 命令行工具不会告诉你；
- 哪几条是「无解」（源图本身就没有横图，只能从视频抽帧重做）→ 记在文档里，没人看。

所以把它做成面板上的一个页：**摊开看 → 一键修 → 顺势让 Emby 重算形状**。

## 二、页面做什么

`GET http://<host>:5081/posters`（导航栏「🖼️ 海报体检」，与 一键入库 / 任务监控 / avdb 连接器 并列）

- **顶部四张卡**：条目总数 / 已是横图 / 可整改 / 无解（按库分列）。
- **操作区**：
  - `🛠 一键整改全部可修项` —— 把每条「竖条 poster + 目录里有更宽横图」的条目就地换成横图；
  - `🔄 刷新 Emby（两库条目）` —— 逐条 `POST /Items/{id}/Refresh`，让 Emby 重读本地文件、重算
    `PrimaryImageAspectRatio`（卡片形状的依据）；
  - `🔍 重新扫描` —— 重跑体检；
  - `☑ 整改后自动刷新对应条目`（默认勾选）。
- **明细表**：库 / 条目（相对路径）/ poster 尺寸 / **文件 AR** / 可用横图 / **Emby AR** / 状态 / 说明 / 单条「整改」按钮。
  - 状态四态：`已是横图`（绿）/`可整改`（黄）/`无解`（红）/`无 poster`（灰）；
  - **Emby AR 与文件 AR 不一致时标 `⚠️待刷新`**（黄）—— 一眼看出「文件换了但 Emby 还没重算」；
  - 筛选器：只看有问题的 / 只看可整改 / 只看无解 / 只看已是横图 / 全部。

## 三、三个接口（都在 `import_api.py` 里注册，实现全在 `poster_page.py`）

| 方法 | 路径 | body / query | 行为 |
|---|---|---|---|
| GET | `/posters` | — | 页面 HTML |
| GET | `/api/posters/audit` | — | 扫描两库 + 读 Emby 侧 AR，返回报告（**只读，不动文件**） |
| POST | `/api/posters/fix` | `{dirs:[...]}` 或 `{mode:"fixable", refresh:"auto"\|"none"}` | 换 poster（旧图备份），`refresh=auto` 时把改过的条目在 Emby 侧定向刷新 |
| POST | `/api/posters/refresh` | `{dirs:[...]}` 或 `{all_libs:true}` | 逐条定向刷新（无 query 的 `/Items/{id}/Refresh`）；`all_libs` 再加一次全库扫库广播 |

## 四、关键设计（为什么这么做）

1. **不重下 provider 图片**。刷新用的是**不带任何 query** 的 `POST /Items/{id}/Refresh`
   —— 这是 `/root/tools/refresh_libs.py` 验证过的用法：Emby 只重读本地文件、重算 AR。
   若用 `ImageRefreshMode=FullRefresh&ReplaceAllImages=true`（`import_api._refresh_emby_path` 的 full 模式），
   Emby 会重新去 provider 抓图，**把刚换好的横图覆盖掉**，反向踩坑。
2. **整改规则三处同源**：`/root/tools/poster_to_wide.py`（命令行存量）、
   `import_api._poster_wide_fix`（入库钩子）、`poster_page.fix_dir`（本页）。
   三处规则必须一致，改一处要同步改另两处（页面文件顶部有醒目注释）。
   规则本身：poster 竖（AR < 1.4）+ 目录里有横图（thumb > fanart > backdrop，AR > 1.4）
   + **横图宽度 ≥ 原 poster 宽度**（防降质）→ 备份旧图、横图写成 `poster.jpg`。幂等。
3. **只管两个根**：`/mnt/g/srtm/已刮削/欧美`、`/mnt/g/srtm/已刮削/无码`。
   路径判断用**路径级**比较（`== 根` 或 `startswith(根 + os.sep)`），
   所以 `已刮削/欧美人造前缀` 不会被误命中；AV / FC2 / 丝袜 / 里番 / 待看 更不会。
4. **备份落点**沿用既有布局：`/mnt/g/srtm/_归档/_trash_海报换缩略图_20260927/<库>/<系列>/<条目>/poster.jpg`
   —— 与命令行工具、入库钩子写的同一处，回滚只需把文件拷回去。
   另有防呆：若算出来的备份路径与源文件同址（异常配置），退回扁平命名，**绝不覆盖源文件**。
5. **不 import import_api**（避免循环）：页面模块只管文件层；Emby 的 host/token/前缀探测
   这些脏活由 `import_api._poster_emby_*` 适配后注入（`_poster_emby_adapter()`）。
6. 服务是 `ThreadingHTTPServer`，扫描/刷新慢一点不会卡住其它请求。
