# 09 · avdb 连接器面板改版（性能 + 真实统计 + 筛选分页）

> 日期：2026-09-28 · 涉及文件：`src/server/avdb_page.py`、`src/server/import_api.py`、`src/server/avdb_source.py`
> 触发：用户反馈「感觉现在的连接器不是很好用啊」，指向 `http://127.0.0.1:5081/avdb`（自研面板页，标题「🔗 avdb 连接器」）

---

## 一、改版前实测到的三个硬缺陷

| 缺陷 | 取证 |
|---|---|
| **接口慢：单次 6.50s** | `/api/avdb/status` 返回 74KB、6.50s；前端 `setInterval(load,15000)` 每 15s 轮询 → 页面长期半卡 |
| **统计失真** | 台账真实 **605 行**（submitted 434 / missing 156 / skipped 14 / waiting 1），面板卡片却显示「已提交入库 148」「跳过/未找到 95」 |
| **待接手永不归零** | 水位 `watermark=606`，`pending_count=6`，但这 6 条全部已在台账里 → 看着像连接器没干活 |

### 根因

1. **`_avdb_seen(limit=300)` + 前端 `seen[:150]`**：`by_status`/`total` 是拿被截断的那批算的 → 数字全错。
2. **每条台账记录线性比对 1634 个已入库名字**：`_imported_names()` 每次调用都重扫 `import_log`（636 行），再把 `thread_id/title/目录名` 展开成 1634 个名字，然后对每行 `same_number()` 线性扫描（实测单条 16ms，150 行 ≈ 2.4s）。
3. **`avdb_source.fetch_downloads()` 先对 article 全表 GROUP BY**：`article` 表 **331,811 行**且 `tid` 无显式索引，先 `GROUP BY tid` 聚合全表再 JOIN `download_log` → 单次 **0.481s**（与 3 行数据无关，纯全表扫描）。
4. **水位被 waiting 行挡住**：`tick()` 遇到 `status='waiting'`（手动提交的磁力，最多等 3 小时、每 5 分钟重查）设 `blocked=True`，水位不推进；而面板「待接手」只按 `id > watermark` 出列表，不排除已进台账的行 → 永远显示 6 条。

## 二、改了什么

### 后端 `import_api.py`

| 新增/改动 | 作用 |
|---|---|
| `_avdb_where(status, q)` | 状态映射（`fail`→submit_failed/adopt_failed/expired；`missing`→missing/not_on_115）+ `q` 对 number/note/dir_name 三列 LIKE |
| `_avdb_counts(status, q)` | SQL 里直接 `COUNT(*)` / `GROUP BY status` → **真实 total / by_status / filtered** |
| `_avdb_seen_page(status, q, limit, offset)` | 台账**分页 + 筛选 + 搜索**读取，不再截断 |
| `avdb_status(status, q, limit, offset)` 重写 | 待接手行**标注** `ledger_status`/`task_id`，新增 `pending_open`（未进台账数）与 `pending_stuck`（水位为何卡住：dl_id/wait_since/tries/ttl_hours） |
| `_imported_names(ttl=60)` | 加 **60s 缓存** + `(系列,数字)` 归一化索引；改用 `mode=ro` 打开 `import_log` |
| `_imported_lookup(number)` | 先查索引，未命中回退线性扫描；**带 memo**（同步到下次名单刷新为止）→ 面板每轮省 0.8s |
| `_avdb_task_map(seen)` | 只对本页行的 task_id 查任务状态 |
| 路由 `/api/avdb/status` | 解析 `status/q/limit/offset` 查询参数 |

### 后端 `avdb_source.py`

`fetch_downloads()` 的 article 回填子查询由「全表 GROUP BY」收窄为「只聚合本窗口出现的 tid」：

```sql
LEFT JOIN (SELECT tid, MAX(number) AS number, MAX(title) AS title
           FROM article
           WHERE tid IN (SELECT tid FROM download_log WHERE id > ?)
           GROUP BY tid) a ON a.tid = d.tid
```

语义不变（窗口内 tid 集合与聚合结果一致），实测 **0.481s → 0.000s**。

### 前端 `avdb_page.py`（整体重写）

- 卡片改真实统计并可点击当筛选器：守护状态 / 台账总计 / 待接手（副标题「其中未处理 N 条」）/ 已提交入库 / 未找到落点 / 等待落点 / 失败 / 跳过。
- 新增筛选条：全部·已提交·未找到·跳过·等待落点·失败 chips + 番号/说明搜索框（Enter 生效）+ 每页 100/200/50。
- 台账标题「匹配 X / 共 Y 条（已筛选）」+ 分页器（上一页/下一页 + 区间）。
- 待接手表新增「台账状态」列（未处理显示灰字），标题「水位之后 N 条，其中未进台账 M 条」。
- 新增 `#stuckBox`：水位被 waiting 行挡住时给蓝色说明条 —— 「已进台账的行标了状态，不是没处理」。
- 轮询周期 15s → **30s**；补齐 waiting/ledger/expired/skipped 的 pill 样式。

## 三、实测结果

| 项 | 改版前 | 改版后 |
|---|---|---|
| `/api/avdb/status` 冷调用 | 6.50s / 74KB | **1.2–1.4s**（首轮补 memo） |
| `/api/avdb/status` 热调用（30s 轮询常态） | 6.50s | **0.00–0.01s** |
| `fetch_downloads`（水位后 100 条） | 0.481s | 0.001s |
| `ledger.total` | 300（截断值） | **605（真实）** |
| `by_status` | 由截断数据统计 | `{submitted:434, missing:156, skipped:14, waiting:1}` |
| 筛选用例 | 无 | `?status=missing&limit=100` → 156 条；`?status=submitted&limit=200` → 434 条；`?q=FC2` → 65 条；`?status=missing&offset=100&limit=100` → 56 条；`?status=fail` → 0 条 |
| 待接手语义 | 6 条「待处理」 | 6 条中 **未处理 0 条**（全部已进台账，面板明说） |
| 水位卡住原因 | 不可见 | `pending_stuck = {dl_id:607, since:'2026-09-28 17:25:54', tries:10, ttl_hours:3}` |

验证方式：
- `python3 -m py_compile` 两个文件通过；`systemctl is-active sehuatang-import.service` = active。
- HTTP 实测脚本 `/tmp/panel_test.py`（筛选/搜索/分页/耗时/待接手标注）。
- 微基准 `/tmp/prof_panel.py`、`/tmp/prof_avdb_q.py`（定位到 article 全表 GROUP BY 这个 0.48s 热点）。
- 无头冒烟 `/tmp/smoke_page.js`：用 DOM 桩在 node 里跑面板 JS，验证 `load()/setFilter()/page()` 无运行时错误，卡片显示 605/434/156/1/0/14、筛选「未找到」= 156 条、翻页 101–200、搜 FC2 = 65 条。

## 四、顺带取证的结论

- 面板「未找到落点」里的 FC2 条目（如 `FC2-2238344`/`FC2-4970939`/`FC2-4972431`）现在会显示 `imported_task` —— 台账状态是 missing（早先查 115 时没找到落点），但该番号其实**已经在库里**（走订阅落点入的库）。这是 chunk-33 修完 FC2 归一化后的正确表现，不是新问题。
- 真正的 156 条 missing 大多是「avdb 记录是 `未分区/未分类`、115 上确实没有该番号目录」或欧美长文件名落点（如 `BLACKED.2016.11.06`）—— 现在可以用筛选 + 搜索定向看了，无需再翻 150 条。

## 六、遗留项

1. `avdb_watch` 水位被 waiting 行挡住时**不推进**是设计取舍（防重复接手），面板现在把它显式解释了；要不要改成「跳过 waiting 行继续推进」需产品决策。
2. 冷调用仍有 ~1.2s（首次为 51 条 missing 补 memo + 重扫 import_log）。若要求恒定毫秒级，可把 `_imported_names` 改成常驻内存 + 定时刷新线程。
3. 面板没有「只给 FC2 落单独目录」的把手（根因在 avdb 侧，见 chunk-33）。
